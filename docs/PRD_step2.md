# PRD 2단계: 지원, 투표, 모집 마감, 팀 규칙, 다른 사람의 변경 보기

## 1. 요약

- 2단계는 학생이 팀에 지원하고 팀원이 투표하며, 관리자가 모집을 마감하는 흐름과 그 규칙(공고 2.3절~2.5절 1, 2항)을 만듦
- 이 단계가 끝나면 연습용 시나리오 3개의 단계 가운데 AI 배정 앞까지를 앱으로 끝까지 진행할 수 있음. 쉬움 1~5단계, 중간 1~10단계, 어려움 1~14단계임
- 3장 표(중간과제 공고 3장, 기능별 쉬운 해결과 어려운 해결)의 어려운 해결 3개를 이 단계에서 만듦

| 기능 | 어려운 해결 | 공고 점수 | 이 문서 |
|---|---|---|---|
| 다른 사람의 변경 보기 | 바뀐 부분만 자동으로 다시 표시(`st.fragment`) | 1점 | PRD_step2 8장(다른 사람의 변경 보기) |
| 필수 포함 역할을 지킬 수 없는 팀 | 지원 단계에서 필수 포함 역할 자리가 모자라게 되는 지원을 막음 | 7점 | PRD_step2 3장(규칙), 4장(지원) |
| 같은 팀에 대기 중인 지원이 여럿 | 승인 직전에 규칙을 다시 검사하고, 투표가 끝난 순서로 처리 | 3점 | PRD_step2 5장(투표) |

- 마지막 정원에 2명이 동시에 들어가는 경우는 1단계의 DB 제약(PRD_step1 4.3절, 제약과 목적)과 PRD_step2 7장(동시 처리)의 잠금으로 함께 막음
- AI 배정, 배정안 검사, 확정은 PRD_step3 1장(요약)에서 다룸

## 2. 전제와 용어

- PRD_step1의 테이블, 로그인, 명단 올리기가 동작한다고 전제함
- 이 문서에서 "공고"는 `중간과제 공고.pdf`임
- 필수 포함 역할은 기획자와 웹 프로그래머임. 팀마다 서로 다른 학생이 1명씩 맡아야 함(공고 2.3절, 팀 규칙)
- 역할 집합: 학생 1명이 맡을 수 있는 역할은 주 역할 1개와 보조 역할의 합집합임
- 테이블 이름은 모두 `tf_mp_`로 시작함

## 3. 규칙

규칙은 DB를 만지지 않는 순수 함수로 `mp/rules.py`에 모음. 지원 접수, 승인 직전 검사, 마감 뒤 배정안 검사(PRD_step3 4장)가 같은 함수를 씀. 같은 규칙을 3곳에 따로 쓰면 결과가 어긋나기 때문임.

### 3.1 규칙 목록

| 번호 | 규칙 | 위반 조건 | 공고의 근거 |
|---|---|---|---|
| R1 | 정원 | 인원이 4명을 넘음 | 공고 2.3절(팀 규칙), 2.4절(팀이 꽉 참) |
| R2 | 주 역할 중복 없음 | 주 역할이 같은 학생이 2명 이상 | 공고 2.3절(팀 규칙) |
| R3 | 필수 포함 역할 점검 | 부족 수가 남은 정원보다 큼(PRD_step2 3.2절, 필수 포함 역할 점검) | 공고 2.3절, 3장 표(필수 포함 역할 자리 계산) |
| R4 | 최소 인원 | 인원이 2명 미만 | 공고 2.3절(팀 규칙). 확정된 구성에만 적용함(PRD_step3 4장) |

- R1~R3은 "이 학생이 들어간 뒤의 팀"에 적용함. R4는 마감 이후 확정할 구성에 적용함

### 3.2 필수 포함 역할 점검 (R3)

- 정의
  - 기획자 후보 집합 P: 기획자를 맡을 수 있는 팀원
  - 웹 프로그래머 후보 집합 W: 웹 프로그래머를 맡을 수 있는 팀원
  - 채울 수 있는 수 m: P와 W가 모두 비어 있지 않고 두 집합의 합집합이 2명 이상이면 2, 합집합이 1명 이상이면 1, 아니면 0
  - 부족 수 = 2 - m
  - 남은 정원 = 4 - 인원
  - R3 위반: 부족 수 > 남은 정원
- m 정의의 근거: 기획자와 웹 프로그래머는 서로 다른 학생이 맡아야 하므로 1명이 둘 다 맡을 수 있어도 1개만 채움(공고 3장 표 아래 설명)
- 공고의 사례로 확인

| 사례 | 계산 | 결과 |
|---|---|---|
| 주 역할이 기획자이고 보조 역할이 웹 프로그래머인 학생 혼자 있는 팀 | m=1, 부족 수=1 | 공고의 "2개 가운데 1개만 채운 것"과 같음 |
| 테스터와 발표자만 있는 2명 팀에 보고서 작성자가 지원 | 들어간 뒤 3명, m=0, 부족 수=2, 남은 정원=1 | 막힘(공고 3장 표의 예) |
| 부록 3(어려움) 단계 11: 팀3에 학생11(TT;PT), 학생15(PT;FD)가 있고 학생14(RW;TT)가 지원 | 들어간 뒤 3명, m=0, 부족 수=2, 남은 정원=1 | 막힘(기대 결과와 같음) |
| 부록 3(어려움) 단계 13: 팀1에 학생1(PL;RW), 학생4(WP;PL), 학생7(FD;PT;TT)이 있고 학생13(RW;PT;FD)이 지원 | 들어간 뒤 4명, P={1,4}, W={4}, m=2, 부족 수=0 | 통과, 대기(기대 결과와 같음) |

### 3.3 함수 목록(구현 시 이름은 바꿀 수 있음)

- `roles_of(student)`: 역할 집합
- `violations_after_join(members, applicant)`: R1~R3 위반 이유 목록(빈 목록이면 통과)
- `required_deficit(students)`: 부족 수

## 4. 지원

### 4.1 접수 검사

지원 단추(`apply_{n}`)를 누르면 서비스 함수가 아래 순서로 검사하고, 처음 걸린 것의 안내를 `result`에 보여 줌. 막힌 지원은 DB에 기록하지 않음(공고 2.4절, 막힌 지원).

| 순서 | 검사 | 안내 |
|---|---|---|
| 1 | 상태가 `open`이 아님 | `막힘: 모집이 마감됨` (명단이 없으면 `막힘: 아직 명단이 올라오지 않음`) |
| 2 | 지원자가 관리자 | `막힘: 학생만 지원할 수 있음` |
| 3 | 이미 팀에 있음 | `막힘: 이미 팀이 있음` |
| 4 | 결과를 기다리는 지원이 있음 | `막힘: 결과를 기다리는 지원이 있음` |
| 5 | 팀이 4명 | `막힘: 팀이 꽉 참` |
| 6 | 같은 주 역할의 팀원이 있음 | `막힘: 같은 주 역할의 팀원이 있음` |
| 7 | R3 위반 | `막힘: 필수 포함 역할(기획자, 웹 프로그래머)을 맡을 학생의 자리가 모자람` |

- 3~7번은 지원자가 들어간 뒤의 팀에 PRD_step2 3장(규칙)의 규칙을 적용한 결과임. 5번은 R1, 6번은 R2, 7번은 R3임
- 7번이 3장 표(필수 포함 역할을 지킬 수 없는 팀)의 어려운 해결임. 대기 중인 지원은 아직 팀원이 아니므로 계산에 넣지 않음. 대기 지원 사이의 충돌은 승인 직전 재검사(PRD_step2 5.2절, 판정)에서 거절로 처리함(공고 2.4절, 승인 직전)

### 4.2 접수한 뒤

- 팀원이 0명이면 지원자를 그 팀의 팀원으로 넣고 지원을 `승인`으로 기록함. 안내는 `승인: 빈 팀이라 바로 팀원이 됨`
- 팀원이 1명 이상이면 지원을 `대기`로 기록함. 안내는 `대기: 팀원 2명의 투표를 기다림`
- 한 학생의 대기 지원은 1개까지임. 이를 DB가 보장하게 부분 유일 인덱스를 둠(아래 DDL)

### 4.3 테이블 추가 (`schema.sql`)

```sql
create table if not exists tf_mp_applications (
  id         bigint generated always as identity primary key,
  team_id    bigint not null references tf_mp_teams(id) on delete cascade,
  student_id bigint not null references tf_mp_students(id) on delete cascade,
  status     text   not null check (status in ('대기','승인','거절')),
  reason     text,
  created_at timestamptz not null default now(),
  decided_at timestamptz
);

create unique index if not exists tf_mp_applications_one_pending
  on tf_mp_applications (student_id) where status = '대기';
```

- 시각은 UTC로 저장하고 화면에 보일 때만 한국 시각(`Asia/Seoul`)으로 바꿈(공고 4.4절, 배포 서버의 시각은 UTC)

## 5. 투표

### 5.1 누가 투표하는가

- 지원이 속한 팀의 현재 팀원임. 투표하는 때의 팀원이 기준이므로 지원한 뒤에 팀원이 된 학생도 투표해야 함(공고 2.4절, 팀원이 있는 팀에 지원)
- 지원자 본인과 다른 팀의 학생은 투표할 수 없음. 안내는 `막힘: 이 팀의 팀원만 투표할 수 있음`
- 한 번 투표하면 바꿀 수 없음(공고 2.4절, 투표 바꾸기). DB 기본 키 `(application_id, voter_id)`가 막고, 서비스는 `막힘: 이미 투표함(바꿀 수 없음)`을 보여 줌
- 이미 결과가 난 지원에 투표하면 `막힘: 이미 결과가 나온 지원임`

```sql
create table if not exists tf_mp_votes (
  application_id bigint not null references tf_mp_applications(id) on delete cascade,
  voter_id       bigint not null references tf_mp_students(id) on delete cascade,
  vote           text   not null check (vote in ('찬성','거부')),
  created_at     timestamptz not null default now(),
  primary key (application_id, voter_id)
);
```

### 5.2 판정

투표를 기록한 직후 같은 트랜잭션에서 아래 순서로 판정함.

1. 거부가 1표라도 있으면 즉시 `거절`(사유 `팀원이 거부함`). 다른 팀원의 투표를 기다리지 않음
2. 현재 팀원 전원이 찬성이면 승인 직전 재검사를 함
   - 지원자가 이미 팀에 있지 않고 상태가 `open`인지, 현재 팀 구성에 지원자를 넣었을 때 R1~R3을 모두 지키는지 확인함
   - 통과하면 팀원으로 넣고 `승인`. 위반하면 `거절`(사유에 위반한 규칙을 적음. 예: `승인 직전 검사: 같은 주 역할의 팀원이 있음`)
3. 위 둘이 아니면 `대기`로 남김. 안내는 `대기: 찬성 1명, 투표하지 않은 팀원 2명`

- `result`에는 그 지원의 지금 상태를 승인, 대기, 거절 중 하나로 시작해 보여 줌(공고 2.7절). 예: `거절: 팀원이 거부함`

### 5.3 처리 순서

- 같은 팀에 대기 중인 지원이 여럿이면, 지원한 순서가 아니라 투표가 끝난 순서로 승인 여부가 정해짐(공고 3장 표의 어려운 해결)
- 이는 판정이 마지막 투표를 기록하는 순간에 일어나므로 별도 대기열 없이 보장됨. 지원 시각순으로 일괄 처리하는 코드를 만들지 않음
- 앞의 지원이 승인되어 팀이 바뀌면 뒤의 대기 지원은 새 팀원의 투표도 받아야 하고, 마지막 투표 시점에 바뀐 팀 구성으로 재검사함
- 대기 중인 지원을 미리 거절하지 않음(공고 2.4절, 승인 직전)

### 5.4 승인 처리

- 정원 번호는 1~4 가운데 비어 있는 가장 작은 번호를 씀
- `tf_mp_members` 삽입이 유일성 제약(`(team_id, slot_no)` 또는 `student_id`)에 걸리면 트랜잭션을 되돌리고, 그 지원을 새 트랜잭션에서 `거절`(사유 `먼저 도착한 지원이 정원을 차지함`)로 기록함

## 6. 모집 마감 (공고 2.5절 1, 2항)

`admin_close` 단추를 누르면 1개 트랜잭션에서 아래를 순서대로 함.

1. 상태를 `open`에서 `closed`로 바꿈. 이미 `open`이 아니면 `막힘: 모집 중일 때만 마감할 수 있음`
2. 대기 중인 지원을 모두 `거절`로 바꿈(사유 `모집 마감`). 이 처리는 승인 직전 재검사와 별개임
3. 팀원이 1명뿐인 팀에서 그 학생을 팀에서 뺌. 학생은 `팀이 없는 학생`이 되고 팀은 빈 팀이 됨
4. 안내: `승인: 모집을 마감함. 대기 지원 3건을 거절하고 1명이 팀에서 빠짐`

- 마감 뒤 지원과 투표는 막힘임(PRD_step2 4.1절 1번, 접수 검사)
- 마감 때 거절된 대기 지원과 팀에서 빠진 학생은 관리자 화면의 `unassigned`로 확인함(공고 2.7절)

## 7. 동시 처리

- 규칙 검사가 바뀐 팀 구성을 보도록, 상태를 바꾸는 모든 서비스 함수는 아래 순서를 지킴
  1. 트랜잭션을 시작하고 `tf_mp_settings`의 `phase` 행을 공유 잠금(`for share`)으로 읽음. 마감은 배타 잠금(`for update`)을 씀
  2. 관련된 팀 행을 `for update`로 잠금. 팀이 여러 개면 `id` 오름차순으로 잠가 교착을 피함
  3. 검사하고 쓴 뒤 커밋함
- 잠금은 규칙 검사의 일관성을 지키고, DB 제약은 마지막 방어선임. 두 지원이 마지막 정원에 동시에 들어가면 먼저 커밋한 쪽만 기록되고 나머지는 재검사에서 거절됨(공고 3장 표의 어려운 해결)
- 트랜잭션 안에서 외부 호출(OpenRouter 등)을 하지 않음

## 8. 다른 사람의 변경 보기 (3장 표의 어려운 해결)

- 로그인한 뒤의 본문 전체를 `@st.fragment(run_every="3s")` 함수 1개에 담음. 간격은 공고의 상한 5초 이하임(공고 2.7절, 5초 이하의 간격). 문서 확인함(context7: `run_every`는 사용자의 상호작용과 별개로 해당 fragment만 주기적으로 다시 실행함)
- 관리자의 AI 배정 영역(`admin_assign`, `assign_status`, `admin_confirm`)은 fragment 밖에 둠(PRD_step3 6장, AI 대기 중 화면)
- 그 밖의 단추와 `result`를 같은 fragment 안에 둠. fragment 안의 위젯을 누르면 fragment만 다시 실행되므로, `result`가 밖에 있으면 갱신되지 않기 때문임
- 단추는 `on_click` 콜백에서 서비스 함수를 호출하고, 결과 문구를 `st.session_state["last_result"]`에 저장함. fragment 본문이 이 값을 `result` 컨테이너에 그림. 저장한 결과는 다음 단추를 누를 때까지 유지함
- 로그인과 로그아웃은 fragment 밖에 둠(전체 다시 실행)
- 한 번 갱신할 때 DB 질의는 연결 1개로 6회 이하로 함(팀, 팀원과 학생, 보조 역할, 대기 지원, 투표, 상태). 갱신이 느리면 서버 안에서 1초짜리 결과 재사용(`st.cache_data(ttl=1)`)을 검토하고, 자기 단추를 누른 뒤에는 그 캐시를 비움. 필요 여부는 측정 뒤 판단함
- 갱신해도 `st.file_uploader`와 `st.number_input`의 상태는 유지됨(확인하지 않았음: 구현할 때 `AppTest`와 브라우저로 확인함)
- `refresh` 단추는 두지 않음. 공고 2.7절(화면 이름 표)은 이 단추를 쉬운 해결로 만든 앱에만 요구함
- 계정이 사라진 세션은 자동으로 로그아웃하고 로그인 화면으로 돌아감(PRD_step1 5.2절, 로그인)

## 9. 화면과 key

### 9.1 학생 화면

| 요소 | 규칙 | key |
|---|---|---|
| 팀 하나 | 팀 이름, 인원, 팀원, 대기 지원(이름과 찬성 현황). 내가 속한 팀은 이름 옆에 `내 팀` | `team_1`, `team_2`, … |
| 지원 단추 | 이미 팀에 속함, 결과를 기다리는 지원이 있음, 모집 마감이면 숨김(공고 2.8절). 정원이 꽉 참, 같은 주 역할, 필수 포함 역할 자리 부족은 단추를 두고 누르면 `막힘`과 이유를 보여 줌 | `apply_1`, `apply_2`, … |
| 찬성 단추 | 내 팀의 대기 지원마다 1개. 이미 투표했으면 숨기고 `내 투표: 찬성`을 보여 줌 | `vote_yes_{지원자 학번}` |
| 거부 단추 | 찬성 단추와 같음 | `vote_no_{지원자 학번}` |
| 내 지원 상태 | `내 지원: 팀2에서 대기 중` 같은 한 줄. 지원이 없으면 표시하지 않음 | 없음 |
| 결과 안내 | 승인, 대기, 거절, 막힘 중 하나로 시작 | `result` |

- 학생 화면에 관리자 단추를 두지 않음. 서비스 함수가 DB로 한 번 더 확인함(PRD_step1 5.2절, 로그인)

### 9.2 관리자 화면

- PRD_step1 5.4절(1단계 화면)에 `admin_close`(`st.button`)를 더함
- `team_n`에 대기 지원 현황을 읽기 전용으로 보여 줌. `unassigned`는 팀이 없는 학생의 이름을 보여 줌
- 관리자 단추의 `result`는 해냈으면 `승인`, 하지 못했으면 `막힘`으로 시작함(공고 2.7절)

## 10. 시험

### 10.1 규칙 단위 시험(`pytest`)

| 대상 | 사례 |

### 10.2 시나리오 재현

- 도구: `AppTest`로 학생마다 별도 앱 세션을 만들어 로그인하고, key로 단추를 눌러 `result`의 첫 단어를 기대 결과와 비교함. 같은 DB를 씀
- 대상: 공고 부록 1(쉬움) 1~5단계, 부록 2(중간) 1~10단계, 부록 3(어려움) 1~14단계. 각 단계의 "하는 일"과 "기대 결과"는 공고 부록의 표를 그대로 씀. 각 시나리오는 CSV를 올려 상태를 초기화한 뒤 시작함
- 특히 확인할 단계

| 시나리오와 단계 | 확인하는 규칙 |
|---|---|
| 쉬움 4 | 거부 1표로 즉시 거절 |
| 중간 3 | 주 역할 중복 막힘 |
| 중간 6 | 일부 찬성 뒤 거부로 즉시 거절 |
| 중간 8 | 대기 지원이 있는 학생의 다른 팀 지원 막힘 |
| 중간 9, 10 | 마감 효과(대기 지원 거절, 1명 팀 해체)와 마감 뒤 막힘 |

| 어려움 13, 14 | 일부 찬성 대기와 마감 거절, 1명 팀 해체 |

### 10.3 동시성 시험

- 빈 팀에 학생 2명이 동시에 지원: 1명은 승인, 1명은 대기가 되고 팀원이 2명을 넘지 않음
- 3명 팀의 대기 지원 2개가 각각 마지막 찬성 1표만 남았을 때 두 투표를 동시에 보냄: 1개 승인, 1개 거절이고 팀은 4명을 넘지 않음
- 방법: 서비스 함수를 스레드 2개에서 동시에 호출함

### 10.4 화면 시험

- 학생 A의 화면을 연 채 학생 B가 지원하면 A의 화면에 5초 안에 반영됨(브라우저 2개로 확인함)
- 공고 2.8절(학생 화면)의 숨김 규칙과 `내 투표` 표시를 확인함
