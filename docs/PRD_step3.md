# PRD 3단계: AI 배정, 배정안 검사, 확정

## 1. 요약

- 3단계는 모집을 마감한 뒤 팀이 없는 학생을 AI가 배정하게 하고, 앱이 배정안을 검사해 관리자가 확정하는 흐름을 만듦(공고 2.5절 3~8항)
- 이 단계가 끝나면 쉬움 6단계, 중간 11단계, 어려움 15단계까지 앱으로 끝낼 수 있음
- OpenRouter 무료 모델 3개를 1차, 2차, 3차 순으로 부름. 모델마다 120초가 넘으면 끊고 다음으로 넘어가며, 3차까지 실패하면 앱이 스스로 배정함
- 확정한 모델: 1차 `nvidia/nemotron-3-ultra-550b-a55b:free`, 2차 `cohere/north-mini-code:free`, 3차 `nvidia/nemotron-3.5-lightning:free`(PRD_step3 5.1절, 모델 3개)
- 3장 표(중간과제 공고 3장, 기능별 쉬운 해결과 어려운 해결)의 어려운 해결 4개를 이 단계에서 만듦

| 기능 | 어려운 해결 | 공고 점수 | 이 문서 |
|---|---|---|---|
| AI 응답이 늦을 때 | 모델마다 120초의 전체 대기 시간을 재서 끊고 다음 모델로 넘어감 | 1점 | PRD_step3 5.4절(모델마다 120초 제한) |
| 3차 모델까지 실패 | 앱이 배정 규칙 5가지를 모두 통과하는 배정을 모든 경우를 따져 끝까지 찾음 | 확정 뒤 규칙 점수(최대 6.5점)와 연결 | PRD_step3 4장(규칙을 지키는 배정 찾기), 5.6절(3차까지 실패) |
| AI 대기 중 화면 | 몇 차 모델의 응답을 기다리는 중인지 보여 줌 | 1점 | PRD_step3 6장(AI 대기 중 화면) |
| 필수 포함 역할 자리를 지킬 수 없는 팀(배정 단계) | 규칙을 지키는 배정이 없으면 AI를 부르지 않고 이유를 안내함 | PRD_step2 1장(요약)의 7점과 함께 | PRD_step3 4장(규칙을 지키는 배정 찾기) |

- 비밀 값은 `.env`와 Streamlit Secrets에서만 읽고 화면과 기록에 출력하지 않음(PRD_step1 3.2절, 비밀 값)

## 2. 전제

- PRD_step1과 PRD_step2가 동작한다고 전제함. 배정은 상태가 `closed`일 때만 함
- 이 문서에서 "공고"는 `중간과제 공고.pdf`이고, 규칙 R1~R4와 필수 포함 역할 점검은 PRD_step2 3장(규칙)의 함수를 그대로 씀
- 테이블 이름은 모두 `tf_mp_`로 시작함

## 3. 배정 흐름

관리자가 `admin_assign`을 누르면 아래 순서로 진행함(공고 2.5절 3~8항).

1. 사전 검사: 관리자인지, 상태가 `closed`인지, 팀이 없는 학생이 있는지, 이미 확정하지 않았는지
2. 규칙을 지키는 배정이 있는지 모든 경우를 따져 확인함(PRD_step3 4장, 규칙을 지키는 배정 찾기). 없으면 AI를 부르지 않고 `assign_status`에 이유를 보여 준 뒤 끝냄(공고 2.5절 8항)
3. 1차 모델을 부름. 응답이 5가지 검사(PRD_step3 4.2절, 배정 검사 5가지)를 통과하면 그 배정안을 씀
4. 실패하면 2차, 3차 모델 순서로 같은 일을 함(공고 2.5절 5항)
5. 3차까지 실패하면 2단계에서 찾은 배정을 앱이 직접 씀(공고 3장 표의 어려운 해결)
6. 검사를 통과한 배정안만 `proposal`에 보여 줌. 학생의 이름과 역할, 배정된 팀을 함께 보여 줌(공고 2.5절 7항)
7. 관리자가 `admin_confirm`을 누르면 배정안을 다시 검사한 뒤 DB에 저장함

- 단추를 누른 결과 안내(`result`)는 배정이 끝난 뒤에 나타남. 공고가 관리자 단추의 `result`를 해냈으면 `승인`, 하지 못했으면 `막힘`으로 시작하라고 하므로(공고 2.7절, 화면 이름 표) 단추의 결과가 배정의 결과를 뜻하게 함
- 채점 프로그램이 배정이 끝나기를 어떻게 기다리는지는 공고에 적혀 있지 않음(확인하지 않았음). 위 이유로 단추를 누른 화면이 끝날 때까지 이어지는 방식을 고름. 진행 중에는 `result`를 비워 두어 이전 결과가 남아 있지 않게 함

## 4. 규칙을 지키는 배정 찾기 (앱의 완전 탐색)

### 4.1 입력과 출력

- 입력: 팀 목록과 팀별 현재 팀원, 팀이 없는 학생 목록(주 역할과 보조 역할 포함)
- 출력: 학생마다 팀 번호를 정한 배정 1개, 또는 "없음"과 그 이유
- 이미 팀에 있는 학생은 옮기지 않음(공고 2.5절 3항)

### 4.2 배정 검사 5가지 (공고 2.5절 4항)

| 번호 | 검사 | 구현 |
|---|---|---|
| 1 | 팀이 없는 학생이 빠짐없이 배정됨 | 응답의 학생 집합이 팀이 없는 학생 집합과 정확히 같음. 모르는 학번, 이미 팀이 있는 학생, 빠진 학생이 있으면 실패 |
| 2 | 한 학생은 한 팀에만 배정됨 | 같은 학번이 2번 나오면 실패. 없는 팀 번호도 실패 |
| 3 | 모든 팀이 2~4명 | 배정 뒤 팀마다 R1(정원)과 R4(최소 인원)를 확인함 |
| 4 | 팀 안에서 주 역할 중복 없음 | R2를 확인함 |
| 5 | 필수 포함 역할 충족 | 배정 뒤 팀마다 필수 포함 역할의 부족 수가 0임. 규칙 R3의 "채울 수 있음"이 아니라 실제로 채운 상태를 요구함 |

- 같은 검사를 AI 응답, 앱 자체 배정, 확정 직전 재검사(PRD_step3 7장, 배정안 표시와 확정)에 모두 씀. 검사 함수는 `mp/rules.py` 1곳에 둠

### 4.3 완전 탐색

- 방법: 팀이 없는 학생을 차례로 팀에 넣어 보는 되돌아가기(백트래킹)로 모든 경우를 따짐. 정원 초과(R1)와 주 역할 중복(R2)이 생기면 그 가지를 자름
- 모든 학생을 넣은 상태에서 PRD_step3 4.2절(배정 검사 5가지)의 검사 3~5번을 통과하는 첫 배정을 돌려줌. 결과는 항상 같게 학번 순서와 팀 번호 순서로 탐색함
- 규모: 공고는 배정 대상이 8명을 넘지 않는다고 예고함(공고 6.2절 9번). 팀 4개이면 4의 8제곱이 65,536가지라서 가지치기 없이도 짧음. 8명을 넘는 경우를 대비해 탐색에 5초의 제한을 두고, 제한에 걸리면 "없음"이 아니라 `규칙을 지키는 배정을 찾지 못함(탐색 시간 초과)`로 안내함. 시간이 걸렸다는 이유로 "없음"이라고 단정하지 않기 위함임
- "없음"일 때 이유 안내는 아래 순서에서 처음 해당하는 것을 씀(공고 2.5절 8항의 예 "팀3에 웹 프로그래머를 맡을 학생이 없음"과 같은 형식)

| 순서 | 조건 | 안내 |
|---|---|---|
| 1 | 전체 학생 수가 팀 수의 4배보다 큼 | `팀 정원(4명)을 모두 합쳐도 학생 수보다 적음` |
| 2 | 전체 학생 수가 팀 수의 2배보다 작음 | `학생 수가 모자라 모든 팀을 2명 이상으로 채울 수 없음` |
| 3 | 어떤 팀에서 기획자 또는 웹 프로그래머를 맡을 수 있는 사람이 그 팀의 팀원과 팀이 없는 학생을 통틀어 아무도 없음 | `팀3에 웹 프로그래머를 맡을 학생이 없음` |
| 4 | 위에 해당하지 않음 | `모든 경우를 따져 보았지만 규칙을 모두 지키는 배정이 없음` |

- 3번은 충분조건 하나를 알려 주는 진단이며, 모든 "없음"의 원인을 설명하지는 못함. 그 경우는 4번으로 안내함

## 5. AI 배정

### 5.1 모델 3개

| 순서 | 모델 | 10/30 시험 결과 | 고른 까닭 |
|---|---|---|---|
| 1차 | `nvidia/nemotron-3-ultra-550b-a55b:free` | 1회 시도, 1.7초, 성공 | 첫 시도에 성공했고 가장 빨랐음 |
| 2차 | `cohere/north-mini-code:free` | 1회 시도, 2.2초, 성공 | 1차와 제공 회사가 다름. 한 회사가 한꺼번에 제한을 걸 위험을 줄임 |
| 3차 | `nvidia/nemotron-3.5-lightning:free` | 1회 시도, 2.2초, 성공 | 첫 시도에 성공함 |
| 예비 | `poolside/laguna-s-2.1:free` | 2회 시도, 1회 429 뒤 3.4초에 성공 | 1~3차 가운데 하나가 쓸 수 없게 되면 교체함 |
| 제외 | `google/gemma-4-31b-it:free` | 2회 시도, 모두 429 | 반복해서 거절됨 |
| 제외 | `thinkingmachines/inkling:free` | 1회 시도, 403(에이전트 도구 안에서만 쓸 수 있다는 응답 문구) | 일반 API 호출을 막는 것으로 보임 |

- 시험은 "대한민국의 수도"를 묻는 짧은 질문 1개로 했고, 모델당 1~2회뿐임. 실제 배정 요청에서의 응답 시간과 성공률은 확인하지 않았음. 구현 뒤 연습용 시나리오로 측정해 순서를 바꿀 수 있고, 바꾸면 README의 모델 이름(공고 7.1절, README.md 양식 4항)도 함께 고침
- 모델 목록은 `mp/config.py`의 상수 3개로 둠. 모든 이름이 `:free`로 끝나는지, `openrouter/free`가 아닌지 시작할 때 확인함(공고 6.3절 14번, 감점)

### 5.2 요청

- 주소: `https://openrouter.ai/api/v1/chat/completions`. 10/30 시험 호출이 이 주소로 성공함(확인함)
- 인증은 `Authorization` 헤더로만 보냄. 헤더와 요청 전체를 기록하거나 오류 문구에 넣지 않음
- 본문
  - `messages`: 규칙과 입력 데이터를 설명하는 사용자 메시지 1개와 "JSON만 답하라"는 시스템 메시지 1개
  - `reasoning`: `{"effort": "low"}`
  - `max_tokens`: 4000. 추론 토큰이 `max_tokens`를 소모해 빈 응답이 나올 수 있으므로 넉넉하게 줌. 문서 확인함(context7: 추론 토큰은 `max_tokens`에 포함되며, 다 쓰면 `finish_reason: "length"`와 빈 `content`가 돌아옴)
- 입력 데이터는 지금의 팀 구성과 팀이 없는 학생임(공고 2.5절 3항). 팀 구성에는 팀 번호, 팀 이름, 현재 팀원마다 학번, 이름, 주 역할, 보조 역할을 넣고, 팀이 없는 학생에게도 학번, 이름, 주 역할, 보조 역할을 넣음. 이름은 가상 명단의 이름이고, 응답에서는 학번으로 학생을 가리키게 함
- 응답 형식: `{"assignments": [{"student_no": "2026101", "team_no": 1}, …]}`. 코드 블록이나 앞뒤 설명이 붙어도 첫 `{`부터 마지막 `}`까지를 읽어 봄

### 5.3 응답 처리와 실패 분류

모든 실패는 다음 모델로 넘어가는 조건이고, 같은 모델을 다시 부르지 않음(공고 4.3절, AI 모델).

| 분류 | 조건 | 기록(`outcome`) |
|---|---|---|
| 성공 | 형식이 맞고 PRD_step3 4.2절(배정 검사 5가지)의 5가지 검사를 모두 통과 | 성공 |
| 검사 실패 | 형식은 맞지만 PRD_step3 4.2절의 검사 1~5번 중 하나라도 어김. 어긴 번호를 `detail`에 적음 | 검사 실패 |
| 빈 응답 | `content`가 비었거나 공백뿐. `finish_reason`을 `detail`에 적음 | 빈 응답 |
| 형식 오류 | JSON을 읽을 수 없음 | 형식 오류 |
| 시간 초과 | 호출한 때부터 120초가 넘음 | 시간 초과 |
| HTTP 오류 | 상태 코드가 400 이상. 429 포함. 코드를 `detail`에 적음 | HTTP 오류 |
| 연결 오류 | 연결 예외. 예외 종류만 `detail`에 적음 | 연결 오류 |

### 5.4 모델마다 120초 제한 (3장 표의 어려운 해결)

- 호출한 때부터 응답을 받을 때까지의 전체 대기 시간을 잼. 응답이 천천히 오다가 120초를 넘는 경우도 끊음(공고 3장 표)
- 방법: 모델 1개를 부를 때 `ThreadPoolExecutor`의 작업 스레드 1개에 `requests.post(timeout=(10, 125))`를 맡기고, 주 흐름은 1초씩 `future.result(timeout=1)`로 기다리며 경과 시간을 잼. 120초가 되면 결과를 기다리지 않고 포기하고 `shutdown(wait=False)`로 풀어 줌. 작업 스레드는 `requests`의 125초 제한에 걸려 스스로 끝나고, 늦게 온 결과는 버림
- 120이라는 수는 `mp/config.py`의 상수 1개에 둠. 시험에서는 이 상수를 바꿔 1초 제한으로 시간 초과를 재현함

### 5.5 전체 시간

- 최악의 경우 3 × 120초 + 완전 탐색 몇 초이므로 약 6분임. 공고 6.3절(감점) 18번의 10분보다 짧음
- 3차까지 실패하면 즉시 앱 자체 배정으로 넘어가므로 대기 시간이 더 늘지 않음

### 5.6 3차까지 실패

- PRD_step3 4.3절(완전 탐색)의 탐색이 이미 끝나 있으므로(PRD_step3 3장 2번, 배정 흐름) 그 결과를 그대로 배정안으로 씀. 출처를 `앱이 직접 배정`으로 표시함
- 앱 자체 배정도 PRD_step3 4.2절(배정 검사 5가지)의 검사를 통과한 것만 씀(이미 통과한 해이지만 같은 함수로 다시 확인함)

### 5.7 호출 한도와 개발 중 시험 규칙

- 무료 모델은 계정당 하루 50회, 분당 20회까지 부를 수 있고 실패한 호출도 횟수에 들어감. 채점 기간(11/3~11/4)에는 채점자가 학생의 키로 AI를 부르므로 그 이틀 동안 하루 한도 가운데 30회 이상을 남겨 둠(공고 4.3절, AI 모델)
- 10/30에 모델 시험으로 8회를 썼음(확인함: 첫 시험 4개 모델 4회, 재시험 2회, 3차 후보 2회를 더해 계산함)
- 규칙
  - 실제 모델 호출 시험은 하루 20회 이하로 함. 연습용 시나리오 3개를 한 번 도는 데 3~9회가 듦(공고 4.3절)
  - 11/3과 11/4에는 이 키로 시험 호출을 하지 않음
  - 규칙 시험과 순차 호출 시험은 가짜 호출 함수로 하고 실제 호출을 쓰지 않음(PRD_step3 10.2절, 순차 호출)

## 6. AI 대기 중 화면 (3장 표의 어려운 해결)

- `assign_status` 컨테이너에 진행 상황을 1초마다 갱신해 보여 줌
- 예
  - `1차 모델(nvidia/nemotron-3-ultra-550b-a55b:free) 응답을 기다리는 중: 37초 / 120초`
  - `1차 모델: 시간 초과(120초) → 2차 모델로 넘어감`
  - `2차 모델의 배정안이 검사를 통과함(소요 154초)`
  - `3차 모델까지 실패해 앱이 직접 배정함`
  - `규칙을 지키는 배정이 없음: 팀3에 웹 프로그래머를 맡을 학생이 없음`
- 마지막 안내와 배정안은 `tf_mp_settings`(`assign_status`, `proposal` 키)에 저장해, 화면을 다시 열어도 보이게 함. 명단을 새로 올리면 지움(PRD_step1 5.3절, 명단 올리기와 팀 만들기의 초기화 3번)
- 배정을 실행하는 동안 관리자 세션의 자동 갱신이 실행을 끊지 않도록, 이 영역은 PRD_step2 8장(다른 사람의 변경 보기)의 fragment 밖에 둠
  - `admin_assign`의 `on_click` 콜백이 `assigning=True`를 세션에 두고 이전 `result`를 비움
  - 본문이 `assigning`을 보면 fragment를 자동 갱신 없이(`run_every=None`) 등록하고, 진행 안내를 갱신하며 배정을 실행함
  - 끝나면 `assigning=False`로 되돌리고 `st.rerun()`으로 전체를 다시 그려 3초 갱신을 되살림
- 관리자가 실행 도중 탭을 닫으면 그 실행은 중단됨. 다시 `admin_assign`을 누르면 됨(`assigning`이 11분 넘게 남아 있으면 오래된 값으로 보고 무시함)
- Streamlit이 fragment 자동 갱신과 전체 실행이 겹칠 때 실행을 끊는 방식은 공식 문서에서 직접 확인하지 못했음. 구현할 때 AI 호출을 가짜로 느리게 만들어 90초 동안 끊기지 않는지 시험함(PRD_step3 10.2절, 순차 호출)

## 7. 배정안 표시와 확정

### 7.1 표시

- `proposal` 컨테이너: 학생 이름, 주 역할과 보조 역할, 배정된 팀. 배정 뒤 팀 구성도 함께 보여 줌. 출처(몇 차 모델 또는 앱이 직접 배정)를 한 줄로 적음
- 검사를 통과하지 못한 배정안은 보여 주지 않음(공고 2.5절 7항)

### 7.2 확정

`admin_confirm`을 누르면 1개 트랜잭션에서 아래를 함. 모두 PRD_step2 7장(동시 처리)의 잠금 순서를 따름.

1. 관리자인지, 상태가 `closed`인지, `proposal`이 있는지 확인함. 없으면 `막힘: 확정할 배정안이 없음`
2. 팀을 `id` 오름차순으로 잠그고 현재 팀원과 팀이 없는 학생을 다시 읽음
3. 배정안의 학생 집합이 현재 팀이 없는 학생 집합과 같은지, PRD_step3 4.2절(배정 검사 5가지)의 5가지 검사를 현재 구성으로 다시 통과하는지 확인함. 어긋나면 `막힘: 배정안이 현재 팀 구성과 맞지 않음. 다시 배정해야 함`
4. 학생을 팀에 넣음. 정원 번호는 비어 있는 가장 작은 번호임. 유일성 제약에 걸리면 되돌리고 같은 안내를 보여 줌
5. 상태를 `confirmed`로 바꾸고 `proposal`을 지움. `assign_status`에 `배정안을 확정함`을 저장함
6. 안내: `승인: 배정안을 확정함`

- 확정한 뒤 `admin_assign`과 `admin_confirm`은 `막힘: 이미 확정함`을 보여 줌
- 확정한 뒤 학생 화면의 지원 단추는 숨김(상태가 `open`이 아님). 학생은 팀 목록으로 자기 팀을 확인함
- 새 브라우저로 열어도 확정한 팀 구성이 그대로 남아 있어야 함(공고 6.2절 5번)

## 8. 기록 (README 사례의 근거)

```sql
create table if not exists tf_mp_ai_logs (
  id         bigint generated always as identity primary key,
  created_at timestamptz not null default now(),
  model      text not null,
  attempt_no smallint not null,
  outcome    text not null,
  seconds    numeric(6,1),
  detail     text
);
```

- 모델을 1번 부를 때마다 1행을 기록함. 모델 응답 본문과 요청 내용은 저장하지 않음(키와 학번 노출을 피하기 위함)
- 관리자 화면에서 최근 기록 10행을 접힌 영역에 보여 줌. 시각은 한국 시각으로 바꿔 보여 줌(공고 4.4절, 배포 서버의 시각은 UTC)
- 이 기록과 `assign_status` 화면이 README의 "AI 모델 호출 실패 사례와 그 화면"의 근거가 됨(공고 7.1절, README.md 양식 5항)

## 9. 화면과 key (3단계 요소)

| 화면 요소 | Streamlit 요소 | key |
|---|---|---|
| AI 배정 단추 | `st.button` | `admin_assign` |
| AI 배정 진행 안내 | `st.container` | `assign_status` |
| 배정안 확정 단추 | `st.button` | `admin_confirm` |
| 팀이 없는 학생 표시 | `st.container` | `unassigned` |
| 단추를 누른 결과 안내 | `st.container` | `result` |
| 배정안 표시 | `st.container` | `proposal`(공고 2.7절 표에 없는 요소라 이름은 자유임) |

- 관리자 단추의 `result`: `승인: 배정안을 만듦(1차 모델)`, `승인: 배정안을 만듦(앱이 직접 배정)`, `승인: 배정안을 확정함`
- 막힘의 예: `막힘: 모집을 마감한 뒤에 배정할 수 있음`, `막힘: 팀이 없는 학생이 없음`, `막힘: 규칙을 지키는 배정이 없음`, `막힘: 이미 확정함`, `막힘: 관리자만 할 수 있음`
- 규칙을 지키는 배정이 없을 때의 안내는 `assign_status` 안에 보여 줌(공고 2.7절)
- 학생 화면에는 3단계 단추를 그리지 않음

## 10. 시험

### 10.1 규칙과 탐색(`pytest`)

| 대상 | 사례 |
|---|---|
| 검사 5가지 | 5가지를 하나씩만 어기는 배정안을 각각 만들어 해당 번호로 실패하는지 확인 |
| 완전 탐색 | 연습용 시나리오 3개의 마감 직후 상태(쉬움 6단계, 중간 11단계, 어려움 15단계 직전)에서 해가 나오고 5가지 검사를 통과함 |
| 없음 | 팀3에 웹 프로그래머가 없는 상태를 만들어 `팀3에 웹 프로그래머를 맡을 학생이 없음`을 확인함. PRD_step3 4.3절(완전 탐색)의 이유 4가지를 각각 만듦 |
| 응답 읽기 | 코드 블록, 앞뒤 설명, 형식 오류, 필드 누락, 중복 학번, 없는 팀 번호 |

### 10.2 순차 호출(가짜 호출 함수)

- 호출 함수를 주입해 실제 호출 없이 아래를 확인함

| 사례 | 기대 |
|---|---|
| 1차 성공 | 2차를 부르지 않음 |
| 1차 시간 초과(상수를 1초로 바꿈) | 2차로 넘어가 성공. 기록에 시간 초과 1행 |
| 1차 429, 2차 빈 응답, 3차 성공 | 3차 배정안을 씀. 기록 3행 |
| 1차 검사 실패, 2차 형식 오류, 3차 HTTP 오류 | 앱이 직접 배정하고 출처가 `앱이 직접 배정`임 |
| 3개 모두 120초 지연(가짜 지연) | 총 약 6분 이내에 끝남(시간은 가짜 시계로 줄여 확인함) |
| 가짜 느린 호출 90초 | 관리자 세션의 자동 갱신 때문에 실행이 끊기지 않음(PRD_step3 6장, AI 대기 중 화면의 확인 항목) |
| 잘못된 키로 호출 | 401을 `HTTP 오류`로 분류하고, 화면과 기록 어디에도 키 값이 없음. 진짜 키가 아닌 임시 값을 씀 |

### 10.3 실제 호출

- 연습용 시나리오 3개를 실제 모델로 1번씩 끝까지 돌림(최대 9회). PRD_step3 5.7절(호출 한도)의 한도를 지킴
- 확인: 응답 시간, 실패 분류, 확정 뒤 모든 팀이 2~4명이고 필수 포함 역할을 채우고 주 역할 중복이 없는지
- `tf_mp_ai_logs`의 기록으로 모델 순서를 다시 판단하고 README의 모델 이름과 실패 사례 화면을 모음

### 10.4 확정

- 낡은 배정안(그 사이 팀 구성이 바뀜)은 확정이 막힘
- 확정을 2번 누르면 2번째는 `막힘: 이미 확정함`
- 확정한 뒤 새 세션으로 열어도 팀 구성이 같음

## 11. 완료 기준

- PRD_step3 10장(시험)의 시험이 통과하고, 연습용 시나리오 3개를 배정까지 끝냄
- 코드와 기록과 화면에 `OPENROUTER_API_KEY` 값이 없음(소스 검색과 화면 텍스트 검색으로 확인함)
- 배포까지 마친 것으로 말하지 않음. 배포 뒤 확인은 구현 계획 4.5절(배포와 제출)에 있음
