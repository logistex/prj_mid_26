# PRD 4단계: 연습 시나리오 실행 탭

## 1. 요약

- 결론: 만들 수 있음. 관리자가 단계표 CSV를 올리면, 앱이 그 단계를 지금 있는 지원, 투표, 마감, 배정, 확정 함수로 1개씩 실행하고, 실행 전후의 팀 상태를 나란히 보여 주는 "시나리오 실행" 탭을 기본 화면 안에 추가함(관리자에게만 보임). 처음에는 별도 페이지(`pages/practice.py`)로 만들었다가 기본 화면 안의 탭으로 합침(이 문서 10장 9번)
- 가장 큰 위험은 중간과제 공고 6.3절(감점) 19번임(연습용 시나리오의 이름이나 순서에 맞춰 결과를 미리 정해 둔 코드, 시나리오 점수 0점). 페이지를 꺼도 코드는 저장소에 남으므로 위험은 켜고 끄는 것으로 줄지 않음. 그래서 이 문서 6장(감점 19번을 피하는 방법)의 규칙과 시험으로 막고, 배포한 앱에서도 페이지를 켜 둠(결정, 이 문서 10장 1번)
- 이 문서가 정하는 것과 정하지 않는 것은 아래와 같음

| 정하는 것 | 정하지 않는 것(범위 밖) |
|---|---|
| 기능, 화면 구성, 단계표 CSV 형식, 감점 19번을 피하는 방법, AI 호출 한도, 시험 계획 | 코드 작성, 브라우저로 화면 단추를 누르는 채점 흉내(기존 `tests/test_scenarios.py`가 맡음), 실행 취소 |

- 데이터 파일 3개를 이미 만들었음(코드가 아님): `tests/data/쉬움_단계.csv`, `중간_단계.csv`, `어려움_단계.csv`. 중간과제 공고 부록 1~3의 단계표를 이 문서 5장(단계표 CSV 형식)의 형식으로 옮겼고, 기존 시험의 단계표와 대조했음(이 문서 5.4절, 만든 데이터 파일 3개와 확인)
- 화면은 좌우로 나눔: 좌측은 시나리오 하위 단계 목록, 우측은 선택한 하위 단계의 이전과 이후 배정 현황(이 문서 4.2절, 좌우 배치)
- 마감, AI 배정, 확정은 같은 `step`에 있어도 화면에서 각각 하위 단계(예: 11-1, 11-2)로 나눔. CSV는 바꾸지 않음(이 문서 5.5절, 하위 단계로 나누는 규칙)

- 채점하는 동안(채점 프로그램을 돌릴 때와 손으로 조작할 때 모두) 이 탭을 쓰지 말라는 안내를 탭 위쪽과 README.md에 1줄로 둠(이 문서 3.5절, 권한과 안내)
- 결정 8건은 모두 정해짐(이 문서 10장)

## 3. 기능

### 3.1 흐름

1. 관리자가 기본 화면에서 로그인하고 "시나리오 실행" 탭을 엶(로그인은 기본 화면의 것을 함께 씀)
2. 명단 CSV, 팀 수, 단계표 CSV를 올리고 "시나리오 시작"을 누름
3. 앱이 먼저 검사함: 단계표 형식, 단계표의 학번이 명단에 있는지, 팀 번호가 팀 수 이하인지. 1개라도 틀리면 오류 목록만 보여 주고 DB를 건드리지 않음
4. 검사를 통과하면 `service.start_roster`로 명단과 팀을 새로 만들고(기본 화면의 `admin_start`와 같은 함수, 기존 팀, 지원, 투표가 모두 지워짐) 하위 단계 전체를 좌측 목록으로 보여 줌
5. 관리자가 좌측 목록에서 하위 단계를 누르면 앱이 하위 단계의 상태에 따라 다르게 함(이 문서 3.2절, 하위 단계와 실행 규칙):
   - 다음 차례인 하위 단계: 행을 위에서 아래로 1개씩 실행하고, 실행 전과 후의 팀 상태를 읽어 저장한 뒤, 우측에 나란히 보여 줌
   - 이미 실행한 하위 단계: 다시 실행하지 않고 저장한 이전과 이후 상태를 우측에 보여 줌. 모든 하위 단계를 끝낸 뒤에 앞 하위 단계를 눌러도 같음
   - 앞 하위 단계를 실행하지 않은 하위 단계: 실행하지 않고 안내만 함
6. 모든 하위 단계를 끝내면 확정한 팀 구성이 규칙을 지키는지 앱의 규칙 함수로 검사해 보여 줌(마지막 `확정` 하위 단계의 규칙 확인)

### 3.2 하위 단계와 실행 규칙

- 하위 단계는 좌측 목록의 1줄임. 같은 `step`의 행을 위에서 아래로 훑으며 `마감`, `배정`, `확정` 행은 행마다 독립한 하위 단계가 되고, 그 사이에 이어진 `지원`, `투표` 행은 묶여서 1개의 하위 단계가 됨. 1개의 `step`이 하위 단계 1개로만 이루어지면 번호는 `step` 그대로(예: `9`), 2개 이상이면 `11-1`, `11-2`처럼 붙임(CSV는 그대로이고 화면에서만 나눔, 이유는 이 문서 5.5절, 하위 단계로 나누는 규칙)
- 만든 데이터 파일 3개의 하위 단계는 아래와 같음. 쉬움은 마감, 배정, 확정이 같은 6단계에 있어 3개로 나뉘고, 중간과 어려움은 마감이 앞 단계(9, 14)에 따로 있어 마지막 단계가 배정과 확정 2개로 나뉨(중간과제 공고 부록 1~3의 단계표 기준)

| 파일 | 하위 단계(순서대로) | 개수 |
|---|---|---|
| `쉬움_단계.csv` | 1, 2, 3, 4, 5, 6-1(마감), 6-2(배정), 6-3(확정) | 8 |
| `중간_단계.csv` | 1~8, 9(마감), 10, 11-1(배정), 11-2(확정) | 12 |
| `어려움_단계.csv` | 1~13, 14(마감), 15-1(배정), 15-2(확정) | 16 |

- 하위 단계는 번호 순서대로만 실행함(앞 하위 단계의 결과 위에 이어지므로). 하위 단계의 상태는 3가지이고, 좌측 목록에서 누르면 상태에 따라 아래와 같이 함

| 하위 단계의 상태 | 조건 | 누르면 하는 일 | 단추 글자 |
|---|---|---|---|
| 다음 차례 | 앞 하위 단계를 모두 실행했고 이 하위 단계는 아직 실행하지 않음 | 실행하고, 이전과 이후 상태를 저장하고, 우측에 보여 줌 | 실행 |
| 실행함 | 이 하위 단계의 기록이 있음 | 실행하지 않고, 저장한 기록을 우측에 보여 줌 | 보기 |
| 대기 | 앞 하위 단계 가운데 실행하지 않은 것이 있음 | 실행하지 않고 "앞 단계부터 실행해야 함"이라고 안내하며, 우측에는 지금 상태 1열을 보여 줌 | 대기 |

- 1개 하위 단계의 행은 CSV에 적힌 순서대로 실행함. 지원과 투표는 행의 `actor` 학생이 한 것으로 부르고, 마감, 배정, 확정은 로그인한 관리자가 한 것으로 부름
- 건너뜀 규칙(중간과제 공고 부록, 지원이 막혔으면 그 지원에 대한 뒤의 투표는 건너뜀): 같은 하위 단계 안에서 지원 행의 실제 결과가 "막힘"이면, 그 지원자를 `target`으로 하는 뒤의 투표 행은 실행하지 않고 "건너뜀"으로 표시함. 건너뛸지는 실제 결과로만 정함
- 이미 실행한 하위 단계는 다시 실행하지 않음("보기"는 DB를 읽지도 않고 저장한 기록만 보여 줌). 되돌리기는 없고, 다시 하려면 "시나리오 시작"을 다시 누름
- 단추를 누르는 즉시 실행하지 않고, 콜백이 "실행 요청"을 세션에 적은 뒤 스크립트 본문에서 실행함(기존 `streamlit_app.py`의 `on_assign`과 `assigning`이 쓰는 방식). 실행하는 동안에는 모든 하위 단계 단추를 비활성으로 그림. 단추를 연속으로 눌러도 1번만 실행되게 하려는 것임
- 실행 도중에 끊기면(새로 고침, 브라우저 닫기) 기록을 쓰기 전에 끝나므로, 그 하위 단계는 기록이 없고 DB에는 일부만 반영된 상태가 됨. 세션에 "실행 중" 표시를 먼저 남기고 기록을 쓸 때 지워서, 표시만 남은 하위 단계를 "중단됨"으로 안내하고 더 진행하지 않음(다시 시작해야 함). 새로 고침으로 세션 상태가 사라지면 이 표시도 사라지므로 이 경우는 이 문서 3.7절(단계 기록 저장)의 "기록 없음" 안내로 처리함
- 하위 단계 실행 중에 오류가 나면(DB 오류 등) 그 행에 오류 종류만 표시하고 멈춤. 접속 정보는 표시하지 않음(기존 `guarded`와 같은 방침)

### 3.3 판정

행마다 실제 결과의 첫 단어(`Result.status`, 승인, 대기, 거절, 막힘 가운데 1개. 화면의 result 글 `"승인: …"`의 첫 단어와 같은 값)를 CSV의 `expected`와 비교함.

| 판정 | 조건 |
|---|---|
| 일치 | `expected`가 있고 실제 결과와 같음 |
| 불일치 | `expected`가 있고 실제 결과와 다름 |
| 비교 없음 | `expected`가 비어 있음 |
| 건너뜀 | 이 문서 3.2절(단계 실행 규칙)의 건너뜀 규칙에 걸림 |
| 미실행 | 아직 실행하지 않음 |

하위 단계의 판정은 그 하위 단계의 행 판정을 모아서 정함: 불일치가 1개라도 있으면 불일치, 일치가 1개 이상이고 불일치가 없으면 일치, 전부 비교 없음이나 건너뜀이면 비교 없음.

### 3.4 전후 비교

하위 단계를 실행하기 직전과 직후에 `service.load_view`로 상태를 읽고(`phase`, 팀별 팀원, 팀별 대기 지원과 찬성 수, 팀이 없는 학생), 순수 함수 `diff_views(before, after)`로 차이를 계산함.

| 구분 | 내용 | 표시 |
|---|---|---|
| 새 팀원 | 후에 있고 전에 없는 팀원 | `+ 학생`, 초록 |
| 빠진 팀원 | 전에 있고 후에 없는 팀원 | `- 학생`, 빨강 |
| 대기 지원 | 새로 생김, 없어짐, 찬성 수 변화 | `대기 +`, `대기 -`, `찬성 1/2 → 2/2`, 주황 |
| 팀이 없는 학생 | 새로 생김, 없어짐 | `+`, `-`와 목록 전체를 따로 강조 |
| 단계(`phase`) | 모집 중 → 모집 마감 → 배정 확정 | 문구 |

- 색만으로 뜻을 전하지 않고 기호(`+`, `-`)와 글을 함께 씀
- 이전과 이후 상태는 단계 기록으로 저장함(이 문서 3.7절, 단계 기록 저장). 차이는 저장하지 않고 보여 줄 때 저장한 이전과 이후에서 다시 계산함

**하위 단계 종류별로 이전 열, 이후 열, 이후 열 아래에 보이는 것**

| 하위 단계 | 이전 열 | 이후 열 | 이후 열 아래 |
|---|---|---|---|
| 지원과 투표의 묶음 | 실행 직전 상태 | 실행 직후 상태 | 변화 요약 |
| 마감 | 마감 직전 상태 | 마감 직후 상태(팀에서 빠진 학생, 거절된 지원이 드러남) | 변화 요약 |
| 배정 | 마감 뒤의 팀과 팀이 없는 학생 | 배정안: 팀마다 새로 들어갈 학생을 `+`로 보이고, 팀이 없는 학생은 없어짐 | 검사 5가지의 통과 여부, 배정안의 출처, 실패한 모델의 기록 |
| 확정 | 배정안을 반영하기 전(배정 하위 단계의 이전과 같은 팀 구성. 배정안은 확정하기 전까지 DB의 팀에 반영되지 않음) | 확정한 최종 팀 | 규칙 확인 4가지 |

**배정 하위 단계의 이후 열 아래**
- 검사 5가지의 통과 여부: 아래 표의 5가지를 각각 "통과"나 "실패(이유)"로 보여 줌. 기존 `rules.check_assignment`는 처음 어긴 1가지만 알려 주므로, 5가지를 각각 따로 계산하는 `rules.assignment_checks`를 추가함(기존 함수는 고치지 않음). 둘의 결과가 어긋나지 않는지 시험함(이 문서 8장, 시험 U-7)

| 번호 | 검사 | 기존 `check_assignment`의 번호 |
|---|---|---|
| 1 | 팀이 없는 학생이 빠짐없이 배정되고, 팀이 없는 학생이 아닌 학번이 없음 | 검사 1번 |
| 2 | 한 학생이 1번만 배정되고 팀 번호가 있는 팀임 | 검사 2번 |
| 3 | 배정한 뒤 모든 팀이 2~4명임 | 검사 3번 |
| 4 | 팀 안에서 주 역할이 같은 학생이 없음 | 검사 4번 |
| 5 | 모든 팀이 필수 포함 역할(기획자, 웹 프로그래머)을 채울 수 있음 | 검사 5번 |

- 출처: 기존 `generate_proposal`이 돌려주는 출처 문구(`1차 모델(이름)`, `2차 모델(이름)`, `3차 모델(이름)`, `앱이 직접 배정`)를 그대로 보여 줌
- 실패한 모델의 기록: 실행할 때 `ai.Progress`가 모은 줄을 그대로 저장해 보여 줌. 기본 화면의 AI 배정 진행 안내와 같은 문구임(예: `1차 모델: 검사 실패(검사 4번: …) → 2차 모델로 넘어감`)
- 실행하는 동안에는 이후 열의 이 자리에 기본 화면과 같은 문구("2차 모델(이름) 응답을 기다리는 중: 24초 / 120초")를 1초마다 갱신해 보여 줌
- 규칙을 지키는 배정이 없어 배정안이 만들어지지 않으면, 이후 열 자리에 결과 안내("막힘: 규칙을 지키는 배정이 없음")와 이유를 보여 줌

**확정 하위 단계의 이후 열 아래**: 규칙 확인 4가지를 표(규칙, 결과, 위반 내용)로 보여 줌. 결과는 "○ 통과"(초록)나 "✕ 위반"(빨강)이고 팀 카드의 투표 표시와 같은 기호임. 위반이면 어긴 팀과 학생을 모두 적음(예: `팀1에서 학생2, 학생3의 주 역할이 테스터로 같음; 팀3에서 …`). 새 함수 `rules.final_state_checks`가 확정한 팀 구성에서 계산하고, 배정안 검사 5가지(`rules.assignment_checks`)도 같은 표와 같은 방식의 위반 내용을 씀(2026-11-01 변경. 이전에는 번호 목록이었고 처음 어긴 1개 팀만 적었음).

| 규칙 확인(번호 없이 표의 줄로 보임) |
|---|
| 모든 학생이 팀에 있음(팀이 없는 학생 0명) |
| 팀마다 2~4명임 |
| 팀 안에서 주 역할 중복이 없음 |

### 3.5 권한과 안내

- 관리자만 씀. 화면에서 숨기는 것으로 끝내지 않고 모든 실행 함수가 DB의 `is_admin`으로 다시 확인함(기존 `service`의 방침과 같음). 관리자가 아니면 "막힘: 관리자만 할 수 있음"을 돌려주고 아무것도 실행하지 않음
- 다른 학생의 이름으로 지원과 투표를 부르는 기능이므로, 이 권한 검사가 핵심임(중간과제 공고 6.3절 감점 11번, 학생 계정으로 관리자 기능을 쓸 수 있음과 반대 방향의 위험)
- 배포한 앱에서도 이 탭을 켜 둠(결정, 이 문서 10장 1번). `ENABLE_PRACTICE` 설정은 만들지 않음
- 안내: "시나리오 시작"은 기존 팀, 지원, 투표를 모두 지우므로, 채점하는 동안(채점 프로그램을 돌릴 때와 손으로 조작할 때 모두)에는 이 탭을 쓰지 말라는 안내를 탭 위쪽과 `README.md`에 1줄로 적음
  - 탭 위쪽(`st.warning`, 탭이 열려 있는 동안 보임): `채점하는 동안에는 이 탭을 쓰지 마십시오(채점 프로그램을 돌릴 때와 손으로 조작할 때 모두). "시나리오 시작"은 기존 팀, 지원, 투표를 모두 지웁니다.`

### 3.7 단계 기록 저장

하위 단계를 실행할 때마다 이전과 이후의 배정 현황을 저장해 두어, 모든 하위 단계를 끝낸 뒤에도 좌측에서 앞 하위 단계를 누르면 우측에 그 하위 단계의 이전과 이후가 다시 보이게 함.

**저장하는 것**(하위 단계마다 기록 1개, 키는 하위 단계 번호 `11-2` 같은 문자열)

| 필드 | 내용 |
|---|---|
| 하위 단계 번호 | `9`, `11-1` 같은 문자열 |
| 실행 시각 | 한국 시각 |
| 행별 결과 | 행 순서, 실제 결과(`status`, `message`), 판정(이 문서 3.3절의 5가지), 건너뜀 여부 |
| 이전 상태 | 실행 직전에 `service.load_view`가 돌려준 값 전체(`phase`, 팀, 팀원, 대기 지원과 투표, 팀이 없는 학생) |
| 이후 상태 | 실행 직후에 같은 함수가 돌려준 값 전체. 배정 하위 단계는 배정안을 얹은 상태(`apply_proposal`) |
| 배정 하위 단계만 | 배정안(출처, 학번과 팀 번호의 쌍), 검사 5가지의 결과, 진행 안내 줄(실패한 모델의 기록 포함), 모델 호출 여부 |
| 확정 하위 단계만 | 규칙 확인 4가지의 결과 |

- 차이(`diff_views`)는 저장하지 않음. 같은 이전과 이후에서는 항상 같은 결과가 나오므로 저장할 필요가 없고, 저장하면 이전과 이후와 어긋날 수 있음
- 기록은 하위 단계 실행 직후에 1번 쓰고 고치지 않음. "시나리오 시작"을 누르면 모두 지움
- 이미 실행한 하위 단계를 누를 때는 서비스 함수도 DB도 부르지 않고 이 기록만 읽음
- 어긋남 표시: 하위 단계 N의 이전 상태가 바로 앞 하위 단계의 이후 상태와 다르면(배정안을 얹은 상태는 비교에서 제외하고, 배정 다음 확정은 배정의 이전과 비교함) 다른 곳(학생 화면, 채점 프로그램 등)에서 DB가 바뀐 것이므로, 우측에 "이전 상태가 앞 단계의 이후 상태와 다름"이라고 표시함

**저장 위치: 세션 상태(`st.session_state`, key `practice_records`)로 정함.** 3가지 안을 비교함.

| 기준 | 세션 상태 | DB: 기존 `tf_mp_settings`에 JSON으로 | DB: 새 테이블 |
|---|---|---|---|
| 새로 고침과 앱 잠들기에 견딤 | 아니오(사라짐) | 예 | 예 |
| 스키마 변경 | 없음 | 없음(기존 키-값 표를 씀. 이미 `proposal`을 JSON으로 저장함) | 있음(`schema.sql`, 접두어 `tf_mp_`) |
| 채점에 쓰는 DB에 남는 것 | 없음 | 기록이 남음. `start_roster`는 `phase`, `proposal`, `assign_status`만 지우므로 이 기능이 시작할 때 자기 키를 지워야 함(기본 화면이 부르는 `start_roster`를 고치면 기본 화면에 영향이 감) | 기록이 남음 |
| 여러 관리자가 동시에 | 세션마다 따로 | 공유 | 공유 |
| 코드량 | 가장 적음 | 중간 | 가장 큼 |
| 크기 | 하위 단계마다 수 KB(추정, 측정하지 않았음) | 같음 | 같음 |

정한 까닭 3가지:
1. 이 기능은 1회의 작업 시간에 하위 단계를 차례로 실행해 보는 연습 도구라서 새로 고침에 견딜 필요가 작고, 견디지 못해도 "시나리오 시작"으로 다시 하면 됨
2. 채점에 쓰는 DB, `schema.sql`, 기본 화면이 부르는 `start_roster`를 건드리지 않음. 변경 범위가 작고, 이 기능이 DB에 남기는 것이 하위 단계 실행의 결과(지원, 투표, 팀원)뿐임
3. 가장 단순함

**한계와 대응**
- 새로 고침, 브라우저 닫기, Community Cloud에서 앱이 잠들거나 다시 배포되면 기록이 사라짐. 이때 페이지는 "저장한 기록이 없음. 시나리오를 다시 시작해야 함"이라고 안내하고, 단추를 눌러도 실행하지 않음. DB의 지금 상태를 보고 어느 하위 단계까지 했는지 추정하지 않음(추정이 틀리면 중복 실행할 수 있으므로)
- 화면 녹화 중에 새로 고침하면 기록을 잃으므로 이 점을 사용자가 알아야 함
- 새로 고침 뒤에도 기록이 남아야 하면 DB의 `tf_mp_settings` 안을 씀(스키마 변경이 없는 쪽). 이때는 시작할 때 이 기능의 키를 지우는 처리가 필요함

## 4. 화면 구성

### 4.1 위치

- 기본 화면(`streamlit_app.py`)에서 관리자로 로그인하면 화면 위쪽(제목, 로그인한 사람 표시, 로그아웃 단추 아래)에 `st.tabs(["팀 편성", "시나리오 실행"], key="main_tabs", on_change="rerun")`가 보임. 학생에게는 탭이 없고 지금 화면 그대로임. 설치판(1.66.1)의 Streamlit 소스로 확인한 것: `on_change="rerun"`이면 탭이 상태를 추적해 선택한 탭만 실행되고, 각 탭의 `.open`이 선택 여부를 알려 주며, `key`로 세션 상태에서 선택한 탭을 읽고 바꿀 수 있음
- "팀 편성" 탭이 처음 열리는 탭이고 그 안에 지금 기본 화면(3초마다 다시 그림, AI 배정과 확정 포함)이 그대로 있음. 다른 탭을 보는 동안에는 3초마다 다시 그리지 않음(`team_tab.open`). 채점 프로그램은 탭을 누르지 않고 첫 화면에서 key로 찾음
- 본문 폭: 기본 화면의 `layout="centered"`(본문 736px)는 그대로 두고, "시나리오 실행" 탭이 열려 있는 동안에만 `mp/style.py`의 `WIDE_CSS`로 본문의 최대 폭을 1400px로 넓힘. 학생 화면과 "팀 편성" 탭은 지금 모양과 같음. 다른 탭으로 돌아가면 다음 실행에서 CSS가 빠져 원래 폭이 됨. 선택자 `[data-testid="stMainBlockContainer"]`는 이 앱에서 본문 폭을 잰 요소임(이전 차례에 화면에서 확인함)
- 이 탭의 입력칸과 단추 key는 모두 `practice_`로 시작해 공고 2.7절의 key와 겹치지 않게 함
- 로그인은 기본 화면의 것을 함께 씀(탭 안에 로그인 칸이 없음). 관리자가 아니면 탭 자체가 그려지지 않고, `practice_view.render`도 관리자가 아니면 안내만 보여 줌

- 맨 위에 시나리오 이름과 진행("6단계 가운데 4단계까지 실행함"). 이름은 올린 단계표 파일의 이름에서 확장자와 끝의 "단계"를 떼고 "시나리오"를 붙여 만듦(`쉬움_단계.csv` → "쉬움 시나리오"). 진행은 단계표의 단계(step) 번호 기준이며 하위 단계가 모두 끝난 단계만 셈. 일부만 실행한 단계는 괄호로 밝힘
- 하위 단계 1개가 칸 1개이고 위에서 아래로 시간 순서임. 칸에는 번호(`3`, `6-1`), 요약(길면 줄을 넘김), 첫 줄 오른쪽 끝에 고정한 결과가 있음. 칸은 1줄 카드이고 높이를 고정하지 않아 모든 단계가 펼쳐짐(2026-11-01 변경)
  - 한 줄 요약은 단계표의 행과 명단의 이름으로 만듦: 지원은 "학생7이 팀1에 지원", 투표는 "학생1 찬성", 마감과 배정과 확정은 "모집 마감", "AI 배정", "배정 확정". 이름 끝의 괄호(`학생7(FD;PT)`)는 뗌(`practice.short_name`). 조사 이/가, 은/는은 마지막 글자의 받침으로 고르고, 알 수 없으면 "이(가)"처럼 둘 다 씀
  - 결과는 건너뛰지 않은 마지막 행의 실제 결과임: `○ 승인`(초록), `✕ 거절`(빨강), `… 대기`(주황), `– 막힘`(회색). 색과 함께 기호와 글자가 있고, 상황을 알리는 글이므로 테두리, 바탕, 그림자가 없음(둥근 배지를 쓰지 않음)
  - 배정 단계의 요약에는 누가 배정했는지까지 씀: `AI 안 부름 · 앱이 직접 배정`, `AI N번 부름 · N차 모델의 배정안`, `AI 3번 부름 · 모두 실패해 앱이 직접 배정`(`practice.ai_source_text`, 부른 횟수는 `ai.Progress.called`)
- 누를 수 있는 것과 상황 표시를 마우스를 올리지 않아도 구별되게 함(2026-11-01 변경). 누를 수 있는 것은 늘 보이는 진한 테두리, 채운 바탕, 아래쪽 그림자, 오른쪽 끝의 동작 기호 "›", 동사로 끝나는 글("3단계 실행", "이전 단계 보기", 칸의 "보기 ›")을 가짐. 마우스를 올리면 진한 그림자가 되고 손 모양 커서가 되는 것은 덧붙임임. 상황 표시(결과, "다음 차례", "바뀜", 투표, 팀 카드의 꼬리표)는 테두리, 바탕, 그림자 없이 기호와 색 글자만 쓰고 결과로 끝남
- 실행했고 지금 오른쪽에 보이지 않는 단계는 칸 전체가 단추(key `practice_step_<번호>`, 도움말 "이 단계 보기")임. 누르면 그 단계의 상황이 우측에 나옴. 결과는 단추 위에 겹쳐 놓고 눌림은 단추로 넘김
- 지금 오른쪽에 보이는 단계의 칸은 굵은 파란 테두리, 옅은 파란 바탕, 왼쪽 끝의 "▶"로만 나타냄("보는 중" 글자 없음). 눌러지지 않는 글이며 우측 제목 앞에도 같은 "▶"를 둠
- 아직 실행하지 않은 단계는 흐리게 그리고 누를 수 없음(단추가 아닌 글). 다음에 실행할 단계에는 "다음 차례"(파란 글자)가 있음. 실행은 좌측 칸이 아니라 우측의 "N단계 실행"으로만 함

**우측: 단계의 상황**
- 제목 "▶ N단계의 상황"(N은 `3`, `6-1` 같은 번호). 실행한 단계가 없으면 "시작할 때의 상황"
- 오른쪽 끝에 "N단계 실행" 1개(key `practice_run_next`, 동작 기호 "›")가 다음 차례 단계를 실행함. 다음 차례가 배정이면 위에 모델 호출 토글 상자를 보임(key `practice_ai_on`, 기본값 켬, 이 문서 7장). 토글을 끄고(또는 오늘 한도를 넘겨 켤 수 없어 꺼진 것과 같을 때) 배정 단계를 실행하면 바로 실행하지 않고 확인 창(`practice_confirm_go`, `practice_confirm_cancel`)을 먼저 띄움: "실제 AI 모델 호출이 꺼져 있습니다. 이대로 실행하면 AI를 부르지 않고 앱이 규칙에 맞는 배정을 직접 찾습니다." 단추는 "앱이 직접 배정으로 실행", "취소"임. 실행한 뒤의 문장에는 "AI를 부르지 않음(실제 AI 모델 호출을 껐음). 앱이 규칙에 맞는 배정을 직접 찾음"을 덧붙임
- 모든 하위 단계를 실행하면 실행 단추 자리에 완료 안내(key `practice_finish`)를 둠. 예: "○ 시나리오 끝 · 6단계를 모두 실행함 · 기대와 일치 8/8 · 확정한 팀이 규칙을 모두 지킴". 기대와 다른 하위 단계가 있으면 "불일치 N", 규칙 위반이 있으면 "규칙 위반 N"을 빨갛게 씀. 마지막 단계를 실행한 직후에는 창(`st.dialog`) "시나리오가 끝났습니다"도 한 번 띄움: 실행한 단계 수, 기대와 일치한 하위 단계 수(다르면 그 번호), 규칙 확인 표, 확정한 팀 목록, "닫기". 계산은 `practice.finish_summary`임
- 보기용 단추 "‹ 이전 단계 보기", "다음 단계 보기 ›"(key `practice_prev`, `practice_next`)는 실행한 단계 사이만 움직임
- 일어난 일 한 문장(`practice.narrate`): 실행 기록의 실제 결과(status, message)와 전후 상태로만 씀. 같은 학생이 한 단계에서 지원을 2번 하면 지원 1건마다 문장을 따로 만들어 " / "로 잇고, 투표는 그 학생의 막히지 않은 가장 최근 지원에 붙임. 거절되면 결과가 난 행의 message를 "거절(까닭: …)"로 넣음(예: 팀원이 거부함, 승인 직전 검사: 같은 주 역할의 팀원이 있음). 이전 단계에서 낸 지원에 투표만 있는 단계는 "팀원들이 학생6의 팀2 지원에 투표함 → …"으로 씀. 예: "학생7이 팀1에 지원함 → 팀원 2명의 투표를 기다림 → 학생1 찬성, 학생4 거부 → 거절. 팀1은 그대로이고 학생7은 팀이 없는 학생으로 돌아감". 마감, 배정, 확정은 "모집 마감 → 승인: (서비스가 돌려준 문구)"
- 한 줄: "기대 결과 …, 실제 결과 …, ○ 일치 또는 ✕ 불일치"(key `practice_verdict`, 둥근 배지 없이 기호와 색 글자). 기대 결과는 단계표의 `expected` 열이고 비교는 기록 위에서만 함(이 문서 3.3절, 판정)
- 배정 단계는 배정안의 출처와 검사 5가지와 실패한 모델의 기록, 확정 단계는 규칙 확인 4가지를 이어서 보임(key `practice_checks`, 이 문서 3.4절의 표)
- "이전 상태도 나란히 보기" 토글(key `practice_show_before`): 켜면 판 아래에 이전과 이후를 2개 열로 나란히 보임(key `practice_before`, `practice_after`, 기호 `+`, `−`로 바뀐 것을 표시)
- 판(key `practice_board`, `mp/practice_board.py`): 이전과 이후를 한 판에 겹쳐 바뀐 것만 표시함
  - 팀마다 자리 4칸짜리 카드. 칸 상태: 그대로, 새로 들어옴(초록, `+`), 빠짐(빨강 취소선, `−`), 배정안(`+`와 "배정안" 꼬리표), 빈 자리(점선 칸)
  - 거절된 지원과 막힌 지원의 칩에는 까닭을 한 줄로 보임(결과가 난 행의 message. 모집 마감으로 사라진 지원은 "모집을 마감함")
  - 대기 중인 지원은 점선 칩이고 칩 아래에 팀원마다 투표를 `학생1 ○`(찬성), `학생4 ✕`(거부), `학생2 ?`(회색, 아직 투표하지 않음)로 보임. 거절된 지원은 빨간 취소선 점선 칩과 그 투표, 막힌 지원은 회색 점선 칩임
  - 그 단계에서 바뀐 팀 카드는 굵은 파란 테두리와 "◆ 바뀜"(파란 글자)이 있음
  - 팀 이름 바로 아래 한 줄: `기획자 ○ 학생1 · 웹 프로그래머 ○ 학생4 · 주 역할 중복 없음 ○`. 보조 역할로 채우면 `학생12(보조)`. 못 채운 역할은 확정하기 전에는 `필요`(회색), 확정한 뒤에는 `✕`(빨강). 두 역할은 서로 다른 팀원이 맡고, 주 역할로 맡은 쪽을 먼저 고름(`practice_board.role_fillers`). 주 역할이 같은 팀원이 있으면 `주 역할 중복 ✕ 테스터(학생5, 학생6)`
  - 팀 카드들 위에 전체 상황 한 줄(단계마다): `전체: 팀이 없는 학생 N명 · 인원 2~4명 ○ · 주 역할 중복 없음 ○ · 필수 포함 역할 ○`. 확정하기 전에 못 채운 것은 `남음(N팀)`(회색), 확정한 뒤에는 `✕(N팀)`(빨강)
  - 그 단계 안에서 생겼다가 거절된 지원은 전후 상태에 없으므로 단계표의 행과 실행 기록(`practice.application_outcomes`)에서 모아 보임
  - 아래에 "팀이 없는 학생" 줄: 그 단계에서 들어온 학생은 초록 `+`, 나간 학생은 빨강 취소선 `−`
  - 색만으로 뜻을 나타내지 않도록 기호와 글자(`+`, `−`, 취소선, ○, ✕, ?, "바뀜", "거절된 지원")를 함께 씀. 학생 이름은 HTML로 쓰기 전에 이스케이프함
- 판 아래에 "바뀐 것 목록"(key `practice_summary`)과 "행별 결과"를 접은 상태로 둠. 글로 읽는 사람을 위한 같은 내용임
- 선택한 단계가 없는 상태에서는 지금 DB 상태를 바뀐 것 표시 없이 같은 판으로 보임. 앞 단계의 이후 상태와 이 단계의 이전 상태가 어긋나면 안내를 보임(이 문서 3.7절)

**비율과 폭**
- `st.columns([3, 7])`(좌 30%, 우 70%). 1400px 폭에서 우측은 약 960px이라 팀 카드가 3개 열로 놓임
- 판은 CSS 격자(`repeat(auto-fill, minmax(250px, 1fr))`)라 우측이 좁으면 열 수가 줄어듦

### 4.3 좁은 화면

- 문서로 확인한 사실: `st.columns`는 뷰포트 폭이 640px 이하일 때 위아래로 쌓임(기본값 `wrap=True`). 좌우 분할도 이 폭 이하에서는 위아래로 쌓이고, 우측 안의 이전과 이후 2개 열도 위아래로 쌓임
- 375px에서 보이는 순서: 제목과 로그인, 준비(접힘), 시나리오 이름과 진행, 시간 줄, 단계의 상황(일어난 일, 판). 가로 스크롤이 생기지 않아야 하므로 표 대신 줄 목록을 씀. 모든 단추는 1차 디자인의 규칙(높이 44px 이상, `mp/style.py`)을 따름
- 한계: 단계를 누르면 결과가 목록 아래에 나타나므로 스크롤이 필요함. 완화책 2가지를 둠
  1. 시간 줄 칸 안에 한 줄 요약과 결과 배지가 있어 스크롤하지 않아도 무엇이 일어났고 어떻게 끝났는지 알 수 있음
  2. 우측 머리글에 "N단계의 상황"을 크게 써서 지금 보는 단계를 알게 함
- 대안(미확인): 좁은 화면에서만 배정 현황을 목록 위로 올리는 방법은 CSS 미디어 쿼리가 필요하고 `st-key-` 클래스에 의존함. 이 판에서 되는지 확인하지 않았으므로 기본 설계에 넣지 않음
- 640px와 1024px 사이(태블릿)는 좌우 분할이 유지되나 우측이 좁음. 화면에서 확인해야 함(미확인)

## 5. 단계표 CSV 형식

### 5.1 열

UTF-8(BOM이 있어도 읽음. 명단 CSV와 같은 방침). 첫 줄은 열 이름임. 열 이름은 명단 CSV(`student_no,name,main_role,sub_roles`)와 같이 영문, 값은 한글을 씀.

| 열 | 뜻 | 필수 |
|---|---|---|
| `step` | 단계 번호(1부터 이어지는 정수). 같은 번호의 행이 1개 단계 | 예 |
| `action` | `지원`, `투표`, `마감`, `배정`, `확정` 가운데 1개 | 예 |
| `actor` | 지원과 투표를 하는 학생의 학번. 마감, 배정, 확정은 비움(로그인한 관리자가 함) | 지원, 투표 |
| `team_no` | 지원할 팀 번호. 투표와 관리자 동작은 비움 | 지원 |
| `target` | 투표 대상(지원자)의 학번. 나머지는 비움 | 투표 |
| `choice` | `찬성` 또는 `거부`. 나머지는 비움 | 투표 |
| `expected` | 기대하는 결과의 첫 단어(`승인`, `대기`, `거절`, `막힘`). 비우면 비교하지 않음 | 아니오 |
| `note` | 사람이 읽는 설명. 화면에만 보이고 실행과 비교에 쓰지 않음 | 아니오 |

### 5.2 검사

- 허용하지 않는 것: 알 수 없는 `action`, 알 수 없는 `expected`, 정수가 아닌 `step`이나 `team_no`, 끊어진 `step` 번호, 필수 열이 빈 행, 행 200개 초과, 파일 크기 200KB 초과
- 오류는 모두 모아 "줄 번호: 이유"의 목록으로 보여 줌
- 학번과 팀 번호가 명단과 팀 수에 맞는지는 "시나리오 시작"을 누를 때 검사함(이 문서 3.1절 3번, 흐름)

### 5.3 예(발췌)

```
step,action,actor,team_no,target,choice,expected,note
2,지원,2026104,1,,,대기,학생4(WP;FD)가 팀1에 지원
2,투표,2026101,,2026104,찬성,승인,학생1(PL;RW)이 학생4(WP;FD)에 찬성
6,마감,,,,,승인,관리자가 마감
```

| `tests/data/중간_단계.csv` | 20 | 11 | 중간과제 공고 부록 2(중간) |
| `tests/data/어려움_단계.csv` | 28 | 15 | 중간과제 공고 부록 3(어려움) |

- 확인한 방법: 임시 스크립트(저장소에 넣지 않음)로 기존 `tests/test_scenarios.py`의 단계표(`SCENARIOS`)와 지원, 투표 행을 1행씩 대조했음. 중간과 어려움은 마감 행까지 일치했고, 쉬움은 지원과 투표 12행이 일치했음(기존 시험은 쉬움의 마감을 마지막 단계 함수에서 따로 처리하므로 마감 행 1개가 CSV에만 있음)
- 공고 표를 보고 옮겼고, 단계 수는 파일의 최대 `step` 번호로 확인했음(쉬움 6, 중간 11, 어려움 15)
- 배정과 확정 행은 기존 시험의 단계표에 없어 대조하지 못했음. 중간과제 공고 부록의 마지막 단계("관리자가 배정, 확정")를 옮겼고, 기대 결과는 중간과제 공고 2.7절(관리자 단추는 해냈으면 "승인")에 따라 `승인`으로 적었음
- 공고 부록의 "기대 결과"는 단계의 최종 결과만 적고 있음. 중간 동작(예: 투표가 필요한 지원은 먼저 "대기")의 기대 결과는 공고의 규칙에서 풀이해, 기존 시험이 쓰던 값을 그대로 옮겼음. 이 값은 공고에 직접 적힌 것이 아님(이 문서 10장 미결 5번)
- 막힌 지원 뒤의 투표 행은 기존 시험이 적지 않았지만, 부록의 설명대로 CSV에는 넣고 `expected`를 비워 두었음(중간 3단계, 어려움 11단계). 앱의 건너뜀 규칙이 실제 결과로 건너뛰는지 보여 주는 용도임
- 상태 결과(예: "학생12의 지원은 거절, 학생3과 학생11은 팀에서 빠짐")는 `expected`로 비교하지 않음. 전후 비교(이 문서 3.4절)로 눈으로 확인함

### 5.5 하위 단계로 나누는 규칙

CSV는 지금처럼 같은 `step` 번호에 마감, 배정, 확정 행을 두고, 화면에서 하위 단계로 나눔(결정, 이 문서 10장 7번). 나누는 규칙은 이 문서 3.2절(하위 단계와 실행 규칙)에 있고, 기준은 행의 `action` 종류뿐임.

| 방법 | 장점 | 단점 |
|---|---|---|
| 화면에서 나눔(채택) | 단계표가 중간과제 공고 부록의 "관리자가 마감하고 배정, 확정" 같은 1단계와 1:1로 대조됨. CSV 형식이 그대로라 이미 만든 파일 3개와 이 문서 5.1절(열) 설명을 바꾸지 않음. 나누는 기준이 동작 종류뿐이라 시나리오마다 다른 코드가 없음(이 문서 6.2절, 규칙 1과 5) | 지원과 투표를 임의로 더 잘게 나눌 수는 없음 |
| CSV에 `sub` 열을 추가해 작성자가 나눔 | 어디서든 나눌 수 있음 | 공고의 단계와 대조하기 어려워짐. 작성자가 잘못 나눌 수 있고 형식 설명과 파일 3개를 다시 고쳐야 함 |

- 판정(이 문서 3.3절)은 하위 단계의 행만으로 계산하므로 `expected`는 지금처럼 행에 둠
- 기대 결과가 적힌 행은 지금 파일 3개와 같음. 배정과 확정 행의 `expected`는 중간과제 공고 2.7절(관리자 단추는 해냈으면 "승인")에 따라 `승인`임

## 6. 감점 19번을 피하는 방법

### 6.1 무엇이 걸리는가

중간과제 공고 6.3절(감점) 19번은 연습용 시나리오의 이름이나 순서를 보고 결과를 미리 정해 둔 코드를 시나리오 점수 0점으로 처리함. 이 기능에서 걸릴 수 있는 모양은 3가지임: (가) 코드에 연습 학번, 이름, 단계 번호를 적음, (나) 기대 결과를 실행 함수에 넘겨 결과가 거기에 맞춰짐, (다) 연습용 파일을 앱이 스스로 읽음.

### 6.2 규칙과 확인

| 번호 | 규칙 | 방법 | 확인하는 시험(이 문서 8장) |
|---|---|---|---|
| 1 | 코드에 연습 시나리오의 학번, 이름, 단계 번호를 넣지 않음 | 모든 앱 코드(`streamlit_app.py`, `mp/`)에는 7자리 학번 모양과 `학생숫자(` 모양의 글이 없게 함. 지금 `streamlit_app.py`와 `mp/`의 검색 결과는 0건임(이 문서를 쓰며 `grep`으로 확인함) | 시험 S-1(소스 검색) |
| 2 | 기대 결과는 실행에 쓰이지 않음 | 실행 함수(`practice_run`)는 `expected` 열을 받지 않음. 판정은 실행이 끝난 뒤 `practice.judge`가 따로 계산함 | 시험 S-2(`expected` 열을 모두 틀리게 바꿔도 실제 결과가 같음) |
| 3 | 서비스 함수가 낸 결과는 가공 없이 보여 줌 | 서비스 함수가 돌려준 `Result`의 상태와 문구를 그대로 기록함. 서비스 함수를 부를 수 없는 경우(명단에 없는 학번, 알 수 없는 동작)와 건너뜀만 실행기가 사유를 직접 적음(`mp/practice_run.py`). 이 3가지는 시나리오와 무관한 오류 처리이고 건너뜀 여부는 앞 지원의 실제 결과로만 정함 | 시험 S-3(실제 결과가 DB 상태와 맞음), `tests/test_practice_run.py`의 명단에 없는 학번 시험(이 문서 8장에는 번호가 없음) |
| 4 | 앱은 연습용 파일을 읽지 않음 | 단계표는 관리자가 올린 파일만 읽음. 앱 코드에 `tests/data`나 `_단계.csv` 글이 없게 함 | 시험 S-1(소스 검색) |
| 5 | 연습용이 아닌 시나리오에서도 같은 코드가 동작함 | 이 문서 8장의 시험에서 연습 시나리오와 다른 명단, 다른 순서의 단계표를 실행함 | 시험 S-4 |
| 6 | 탭을 켜 둔 채로 채점과 섞이지 않게 함 | 탭 위쪽과 README에 사용 금지 안내를 둠(이 문서 3.5절, 권한과 안내). 켜고 끄는 설정은 만들지 않음 | 시험 N-1(안내 문구 존재) |

### 6.3 남는 위험

- 규칙 1~5를 지켜도 채점자가 코드를 읽고 "연습 시나리오를 위한 코드"라고 판단할 위험은 0이 아님. 이 기능이 공고가 요구하지 않은 것이고 감점이 시나리오 점수 0점으로 무거움. 페이지를 끄는 것은 이 위험을 줄이지 못하므로(코드는 저장소에 남음) 켜 두기로 정했고, 위험은 규칙 1~5와 시험으로 막음
- README에 이 기능이 "연습 시나리오를 실행해 결과를 보여 주는 도구이고, 결과는 실제 기능이 낸다"고 설명하려면 이 문서 6.2절(규칙과 확인)의 시험 결과를 근거로 적어야 함. 이번에는 안내 1줄과 기대 결과의 출처 1줄만 README에 넣음(이 문서 10장 5번)
- 대안: 이 기능을 페이지로 배포하지 않고 `scripts/`의 실행 도구와 시험으로만 두면 위험이 더 작음. 화면으로 보여 주는 이점은 사라짐. 켜 두기로 한 결정에 따라 채택하지 않음

## 7. AI 호출 한도

**한도에 대해 확인한 것**
- 중간과제 공고 4.3절(AI 모델)이 정한 것: 무료 모델은 계정마다 하루 50회, 분당 20회까지. 실패한 호출도 횟수에 들어감. 채점 기간(11/3~11/4)에는 하루 한도 가운데 30번 이상을 남겨 둠. 연습용 시나리오 3개를 1번 돌리는 데 AI 호출이 3~9번 듦
- OpenRouter의 한도 문서와 FAQ를 이번에 읽었음(하위 에이전트가 2026-10-31에 읽음): 무료 모델의 한도는 "UTC 하루" 단위이고, 누적 구매 크레딧이 10 미만이면 하루 50회, 10 이상이면 하루 1000회임. 분당은 20회임. 이 계정의 크레딧 상태는 모르므로 공고의 50회를 기준으로 삼음
- 초기화 시각: 문서는 "UTC 하루"라고만 적고 시각을 따로 적지 않음. UTC 0시는 한국 시각 09:00이며, 이는 계산한 값임. 집계는 "UTC 0시 이후"로 함
- 문서에는 `GET /api/v1/key` 응답의 `free_model_daily_requests`(used, limit, remaining)가 현재 UTC 하루의 집계를 보여 준다고 적혀 있음. 이 앱 밖의 호출까지 반영하므로 정확하지만, 이번에는 호출해 보지 않았고 키를 쓰는 요청이 1개 늘어나므로 채택하지 않음(미확인)

**이 기능이 부르는 횟수**: 배정 하위 단계 1번에 최대 3회(모델마다 1회, 같은 모델을 다시 부르지 않음. 기존 `ai.propose`). 시나리오 3개를 모델 호출로 1번씩 돌리면 최대 9회임

**설계**
0. 2026-11-01에 기본값을 바꿈: 토글은 켬이 기본임. 무료 모델이라 비용은 문제가 아니고 AI로 배정하는 쪽이 낫다는 판단임(아래 1번과 2번은 이전 판의 문장이며 기본값만 바뀜). 끄고 실행하면 확인 창이 먼저 뜸(이 문서 4.2절)
1. 모델 호출 없이 앱이 직접 배정하는 경로가 있음(토글을 끈 경우). 모델 목록을 빈 목록으로 `service.generate_proposal`에 넘기면 `ai.propose`가 모델을 부르지 않고 앱이 찾은 배정을 쓰는 것을 코드로 확인했음(`mp/ai.py`의 `propose`는 모델 목록을 돌며 부르고, 목록이 비면 `fallback_pairs`를 `앱이 직접 배정`이라는 출처로 돌려줌). 이 경로에서는 호출 횟수가 0임
2. 토글이 켜져 있으면 실제 모델을 부름. 켜면 실제 모델을 부른다는 것이 상자 안 문구에서 보임(이 문서 4.2절, 좌우 배치). 모델은 1차, 2차, 3차를 그대로 씀(공고 4.3절은 `openrouter/free` 라우터를 금지함)
3. 막는 규칙: `오늘 기록 + 3 > 50`이면 토글을 막음(그 실행이 하루 한도를 넘기므로). 상수 3개(`DAILY_LIMIT = 50`, `RESERVE = 30`, `CALLS_PER_RUN = 3`)는 공고에서 가져왔고 코드에 이름으로 둠
4. 경고 규칙: 이 실행 뒤에 남는 횟수(`50 − 오늘 기록 − 3`)가 30 미만이면 "채점 기간(11/3~11/4)에는 하루 30회 이상을 남겨야 함. 오늘이 채점 기간이면 켜지 마십시오" 1줄을 보임. 막지는 않음. 한도는 UTC 하루마다 새로 시작하므로 채점 기간 전날의 사용은 채점 기간의 횟수를 줄이지 않기 때문임(이전 판의 이 문서는 30회 보존까지 막았으나 과하다고 판단해 고침)
5. 집계는 `tf_mp_ai_logs`의 기록임(UTC 0시 이후의 행 수). 이 앱 밖에서 같은 키로 부른 호출은 모르므로, 화면의 횟수는 하한임을 안내 문구로 밝힘
6. 토글을 끄면 모델을 부르지 않고 앱이 직접 배정하므로(위 1번), 연습에서 성공해도 모델을 부르는 채점 경로의 성공을 보증하지 않음. 모델을 부르는 경로를 확인하려면 토글을 켜고 실행해야 함(시험 V-2)
7. 시험에서는 가짜 호출 함수나 모델 호출 없는 경로만 씀. 실제 모델 호출 시험(V-2)은 하지 않고 신 교수 쪽에서 함
